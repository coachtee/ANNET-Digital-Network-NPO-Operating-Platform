# Deploying ANNET on Coolify v4

This is the production deployment path for the ANNET Digital Network & NPO
Operating Platform. ANNET is a standard Dockerfile-based Coolify application:
Coolify builds the image from this repository's `Dockerfile`, runs it, and
fronts it with its built-in Traefik reverse proxy for TLS and domain routing.
PostgreSQL and Redis are separate, first-class Coolify-managed resources —
nothing in this repo bundles or assumes a specific database/cache container.

No `deploy.sh` or other bootstrap script is required or present. All runtime
configuration comes from environment variables set in the Coolify UI. Secrets
(`SECRET_KEY`, database/Redis credentials, the initial admin password) are
**not** generated by anything in this repository — generate them yourself
(e.g. `openssl rand -base64 48` for `SECRET_KEY`) and paste them into
Coolify's environment variable editor, or use Coolify's own "generate" button
where it offers one.

## 0. One-time setup checklist (do this before step 1)

Two things that are easy to configure *after* the first deploy fails, but
cheaper to get right up front:

- [ ] **Domain is assigned to the `web` service specifically**, not just typed
  into a notes field — Coolify → app → **Configuration → Domains**. Until this
  is set, Coolify's `COOLIFY_FQDN` variable is empty, Traefik has no route for
  your hostname, and every request 404s with a plain-text "page not found"
  (Traefik's own stock response, not Django's).
- [ ] **`ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` are set** (see the table in
  step 2) *before* the domain starts receiving real traffic — without them,
  once Traefik does route the request through, Django rejects it with a bare
  `Bad Request (400)` (its stock `DisallowedHost` response).

Both are one-line fixes but only take effect after a redeploy — an env var
change or a domain assignment does not retroactively apply to an already
running container.

## 1. Create the resources

In your Coolify project, create three resources:

1. **PostgreSQL** (Coolify → New Resource → Database → PostgreSQL). Coolify
   provisions it and gives you a connection string — copy it, you'll need it
   as `DATABASE_URL` below.
2. **Redis** (New Resource → Database → Redis). Same idea — copy the
   connection string for `REDIS_URL`.
3. **Application** (New Resource → Application → your Git source →
   this repository). Build pack: **Dockerfile** (Coolify auto-detects the
   `Dockerfile` at the repo root). Port: **8000** (matches `EXPOSE 8000` /
   Gunicorn's bind address below).

Then connect the app to the two database resources so they share a network
(Coolify does this automatically when they're in the same project/environment;
otherwise use "Add resource connection" in the app's Coolify settings).

## 2. Required environment variables

Set these under the application's **Environment Variables** tab in Coolify.
Nothing needs to be edited in the repository itself — this is the entire
runtime configuration surface.

| Variable | Required | Example / notes |
|---|---|---|
| `SECRET_KEY` | **Yes** | Random 50+ character string. Generate with `openssl rand -base64 48`. Never reuse the repo's insecure default. |
| `DEBUG` | Recommended | `False`. Must be `False` in production — enables HSTS, secure cookies, SSL redirect, manifest static storage. |
| `ENVIRONMENT` | Recommended | `production`. Gates demo-data loading (see `LOAD_DEMO_DATA` below) and is shown in a few admin-facing places. |
| `ALLOWED_HOSTS` | **Yes** | `annet.naleli.co.za` (comma-separate multiple hosts, e.g. `annet.naleli.co.za,www.annet.naleli.co.za`). `127.0.0.1`/`localhost` are always additionally allowed for the container-internal health check — see `apps/core/utils.py`. |
| `CSRF_TRUSTED_ORIGINS` | **Yes** | `https://annet.naleli.co.za` (comma-separated, full scheme+host, no path). Required because Traefik terminates TLS in front of the app. |
| `DATABASE_URL` | **Yes** | The connection string Coolify's PostgreSQL resource gives you, e.g. `postgres://user:password@host:5432/dbname`. Takes priority over the `DB_*` variables if both are set. |
| `REDIS_URL` | Recommended | The connection string Coolify's Redis resource gives you, e.g. `redis://:password@host:6379/0`. Without it the app falls back to local in-process caching, which does not work correctly with more than one Gunicorn worker/replica. |
| `SECURE_SSL_REDIRECT` | Optional | `True` (default when `DEBUG=False`). Leave default unless Coolify/Traefik is not terminating TLS for this domain. |
| `SECURE_HSTS_SECONDS` | Optional | `31536000` (default, one year). Set to `0` temporarily if you need to roll back off HTTPS. |
| `ADMIN_EMAIL` | Optional | Address to receive unhandled server-error (HTTP 500) email reports. Leave unset to disable. |
| `EMAIL_BACKEND` / `EMAIL_HOST` / `EMAIL_PORT` / `EMAIL_HOST_USER` / `EMAIL_HOST_PASSWORD` / `EMAIL_USE_TLS` / `DEFAULT_FROM_EMAIL` | Recommended | SMTP settings for outbound mail (password resets, notifications). Without these, mail attempts will fail silently against the default (non-existent) SMTP host. |
| `DJANGO_SUPERUSER_EMAIL` / `DJANGO_SUPERUSER_PASSWORD` | First deploy only | If both are set, the entrypoint creates (or leaves untouched, on re-runs) an initial platform-admin account on every container start. Safe to leave set permanently — it never resets an existing account's password. Remove/rotate the value after first login if you'd rather not keep a plaintext password in Coolify's env var store. |
| `DJANGO_SUPERUSER_FIRST_NAME` / `DJANGO_SUPERUSER_LAST_NAME` | Optional | Defaults to "Platform" / "Administrator". |
| `LOAD_DEMO_DATA` | Optional | `true` to seed demo organisations/data on startup. Only takes effect when `ENVIRONMENT` is not `production` (`LOAD_DEMO_DATA_ALLOWED` in `config/settings.py`) — leave unset in production. |
| `PLATFORM_NAME` / `NETWORK_SHORT_NAME` / `NETWORK_TAGLINE` | Optional | Branding text shown across the site. Defaults are ANNET's own branding. |
| `TIME_ZONE` | Optional | Default `Africa/Johannesburg`. |
| `MAX_UPLOAD_SIZE_BYTES` | Optional | Default `15728640` (15MB). |
| `LOG_LEVEL` | Optional | Default `INFO`. |

Do **not** set `DB_ENGINE`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`/`DB_HOST`/`DB_PORT`
on Coolify — those exist for non-PaaS Docker Compose setups where no single
connection string is provided. `DATABASE_URL` supersedes them.

## 3. Database configuration

Point `DATABASE_URL` at the Coolify PostgreSQL resource's connection string.
`config/settings.py` parses it with `dj_database_url` and sets
`CONN_MAX_AGE=60` for persistent connections. On every container start,
`docker/django/entrypoint.sh` waits for the database to accept connections,
then runs `python manage.py migrate --noinput` automatically — no manual
migration step is needed after deploy.

## 4. Redis configuration

Point `REDIS_URL` at the Coolify Redis resource's connection string. Redis is
used only as the Django cache backend (`django_redis`) — no sessions, queues,
or other state live there, so it can be safely flushed or resized without
any data-loss concern beyond a temporary cache-cold period.

## 5. Persistent volumes

`docker-compose.yml` declares three named volumes, all mounted into the app
container:

| Volume | Container path | Contents |
|---|---|---|
| `static_volume` | `/app/staticfiles` | Collected static assets (CSS/JS/images), rebuilt on every start by `collectstatic`. Not strictly required to persist, but avoids re-running collectstatic's hashing work on a restart. |
| `media_volume` | `/app/media` | Public uploads (organisation/network logos) — **must persist**, served directly by Django (see `config/urls.py`). |
| `private_media_volume` | `/app/private_media` | Private uploads (compliance evidence, expense receipts, governance documents) — **must persist**, served only through authenticated views, never directly by URL. |

If Coolify deploys this as a Dockerfile-based application (not via the
`docker-compose.yml` in this repo), add equivalent **Persistent Storage**
mounts in the Coolify UI for `/app/media` and `/app/private_media` at
minimum — losing that data on redeploy would delete real uploaded files.

## 6. Coolify application settings

- **Build pack:** Dockerfile
- **Port:** `8000` (Gunicorn binds `0.0.0.0:8000` — see `Dockerfile` CMD)
- **Health check path:** `/health/` (see below)
- **Domains:** `annet.naleli.co.za` (Coolify issues/renews the Let's Encrypt
  certificate automatically via Traefik once the domain's DNS points at your
  Coolify host)

## 7. Health check settings

`GET /health/` (`apps/core/views.py`) returns `HTTP 200` with body `OK`. It
requires no authentication, runs no database or cache query, and never
redirects (`SECURE_REDIRECT_EXEMPT` in `config/settings.py` exempts it from
`SECURE_SSL_REDIRECT` unconditionally, and `127.0.0.1`/`localhost` are always
permitted in `ALLOWED_HOSTS` regardless of the configured public domain — see
`apps/core/utils.py:ensure_hosts_present`). This makes it safe for:

- The `Dockerfile`'s own `HEALTHCHECK` instruction (`curl` against
  `http://127.0.0.1:8000/health/` every 30s).
- Coolify's health check configuration — set the health check path to
  `/health/` in the application's **Health Check** settings tab.
- Any load balancer, Kubernetes liveness/readiness probe, or uptime monitor.

## 8. Domain configuration

1. Point `annet.naleli.co.za`'s DNS `A`/`AAAA` record at your Coolify host.
2. Add `annet.naleli.co.za` as the application's domain in Coolify — it
   provisions and auto-renews the TLS certificate via Traefik/Let's Encrypt.
3. Set `ALLOWED_HOSTS=annet.naleli.co.za` and
   `CSRF_TRUSTED_ORIGINS=https://annet.naleli.co.za` (see table above).
4. Traefik terminates TLS and forwards plain HTTP to the container, setting
   `X-Forwarded-Proto`/`X-Forwarded-Host`. `config/settings.py` trusts these
   via `SECURE_PROXY_SSL_HEADER` and `USE_X_FORWARDED_HOST` — required for
   Django to correctly detect the request as HTTPS and avoid a redirect loop.

## Deploying

Once the resources and environment variables above are in place: connect the
GitHub repository, create the PostgreSQL and Redis resources, add the
environment variables, and click **Deploy**. Coolify builds the image from
`Dockerfile`, starts the container, and `docker/django/entrypoint.sh` handles
migrations, static file collection, and (if configured) the initial admin
account automatically — no manual steps or scripts required.

Redeploys (new commits, or clicking **Redeploy** in Coolify) go through the
same entrypoint and are safe to run repeatedly: migrations and
`ensure_superuser` are idempotent.

## Shipping a change: Claude Code → GitHub → Coolify

This is the normal day-2 loop once the app is live — no script, no manual
server access, every step below is either Claude Code or the Coolify UI.

1. **Ask Claude Code to make the change**, in a session pointed at this
   repository. It edits files, runs the test suite (`python manage.py test`)
   and `python manage.py check`, then commits and pushes to the branch
   Coolify is tracking (currently `claude/annet-platform-rc-build-tfew1l`).
   You can review the diff on GitHub before it reaches production.
2. **Coolify picks up the push.** If a GitHub webhook is configured
   (Coolify → app → **Configuration → General** → "Automatic deployment" /
   webhook), a deploy starts automatically within seconds of the push. If
   not, open the app in Coolify and click **Deploy** manually — either way,
   deploys always build from the latest commit on the tracked branch, never
   from uncommitted local state.
3. **Watch the deployment log** (Coolify → app → **Deployments**, or the log
   stream shown live during a deploy). A healthy run looks like: image
   build (or "Build step skipped" if the commit's image is already cached),
   `Rolling update started`, the new container passing its `/health/`
   healthcheck (`Healthcheck logs: OK`), `Removing old containers`, `Rolling
   update completed`. Coolify only cuts traffic over to the new container
   once the healthcheck passes — a bad deploy fails the healthcheck and the
   previous container keeps serving traffic instead of an outage.
4. **Verify:** load `https://annet.naleli.co.za` and click through whatever
   the change touched. `curl -I https://annet.naleli.co.za/health/` should
   return `200`.
5. **If something's wrong,** use Coolify's deployment history to redeploy a
   previous commit/image while you diagnose — the migrations
   `entrypoint.sh` ran are forward-only, so a rollback restores the
   *application code*, not the database schema; check whether the change
   included a migration before assuming a straight rollback is safe.

Nothing in this loop needs SSH access to the server, a `.env` file, or any
of the removed `deploy.sh`/`backup.sh`/`restore.sh`/`update.sh` scripts —
that's the entire point of moving to Coolify.

## Local Docker Compose (non-Coolify)

`docker-compose.yml` in this repo defines the `web` application service only
— it does not bundle Postgres, Redis, or a reverse proxy, matching the
Coolify deployment model. For local development or a non-Coolify Docker host,
run your own PostgreSQL/Redis (or add them as extra services in a compose
override) and set `DATABASE_URL`/`REDIS_URL` in a `.env` file alongside this
repo; `docker-compose.yml` loads it automatically if present (`env_file: .env`,
marked `required: false`). See `.env.example` for the full list of variables
also usable this way.
